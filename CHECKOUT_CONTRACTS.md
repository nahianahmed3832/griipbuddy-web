# Checkout and order contracts (Steps 6–7)

These routes are for synthetic data. They are disabled whenever the recovered catalog API is configured. No route calls production, an actual payment gateway, or a courier. Existing cart, market and account contracts still apply.

| Route | Caller | Contract |
|---|---|---|
| `POST /api/checkout/session` | Storefront | Establishes an opaque 30-day guest cookie, HTTP-only and SameSite=Lax (Secure on HTTPS). Signed-in fixture customers use their account ID. |
| `POST /api/cart/quote` | Storefront | Returns current regional price, available units, discounts and estimated shipping in integer minor units. Unpriced or unavailable lines and unsupported shipping block placement. |
| `POST /api/checkout/place` | Buyer | JSON fields: `key` (UUID), `market`, `method`, `lines` (product ID, variant ID, slug, quantity), optional `coupon`, `review` and `delivery`. `review` echoes the server quote's currency, total, shipping, coupon discount and per-line IDs, quantities and unit prices. The server calculates each value again. `delivery` has `name`, `phone`, `street`, `city`, `region` and `postal`. Manual orders use multipart with these fields in a `payload` JSON part plus `paymentPhone`, `reference` and a single `receipt` file part. |
| `GET /api/checkout/order?id=…` | Owner | Private order status, lines, payment summary, tracking and return state. Omits delivery details, receipt and payment reference. An unknown or unowned order returns 404. |
| `POST /api/checkout/simulate` | Owner | `orderId` and `outcome: captured\|declined`. Runs the same parser and verification as the simulator callback. It cannot approve manual evidence. |
| `POST /api/checkout/webhook/{stripe,paypal}` | Simulated provider | Stripe Checkout Session and PayPal capture-shaped events. The Stripe parser uses raw body, timestamp, `Stripe-Signature` and `livemode: false`; PayPal uses the private fixture issuer's `X-GriipBuddy-Sim-Signature`. A capture must match the stored attempt, provider, order, amount and currency. Invalid, conflicting, stale, late and unknown events cannot confirm orders. |
| `POST /api/checkout/cancel` | Owner | `orderId`. Releases active holds once before dispatch. For a paid order, cancellation opens a refund obligation. |
| `POST /api/checkout/return` | Owner | `orderId`, `kind: return\|refund`, `reason`. A delivered order can have one request. Submission alone changes neither money nor physical stock. |
| `GET /api/checkout/receipt?id=…` | Operator | Returns a rebuilt static JPEG attachment. Add `format=metadata` to see the submitted phone and reference. Both require operator authorization; nothing is served from a public asset path. |
| `POST /api/checkout/operator` | Operator | `orderId` and `action`: `approve-receipt` (exact verified `reference`, `amount`, `currency`), `reject-receipt`, `dispatch`, `deliver` (collected `amount` and `currency`), `accept-return` (after physical return if applicable), or `refund` (confirmed simulated `amount`, `currency`, unique `reference`). Actions use synthetic data only. |
| `GET /api/checkout/reconcile` | Operator | Checks expected stock versus holds and fulfilled orders, payment arithmetic and foreign keys. Returns aggregate counts and totals, no customer data. |

Operator routes accept a local bearer secret of at least 32 characters. Storefront write routes check origin and scope. Order creation returns **201** on success and **200** for the same payload and key in the same buyer scope. Changed quotes, stock, states, or reuse of a key with a different payload return **409**; paused checkout returns **503** for new placement. Operator tokens, original receipts, secrets and raw ledger databases must stay outside Git.

## Order and stock rules

- Reprice, verify regional shipping and reserve every line together in one SQLite transaction against the synthetic stock that also feeds catalog availability. This ledger has no connection to recovered MongoDB.
- Cash on delivery places an order with zero paid. Dispatch consumes the hold and reduces physical stock once. Delivery records only the actual simulated amount collected, once.
- Manual payment holds stock and remains unpaid during review. The default Bangladesh advance is 20%, rounded up to a minor unit, with the remainder due on delivery. The actual configured amount and reference must match verified evidence before the order is placed. A rejection or expiry releases the hold.
- A signed online capture places an order without double-reserving stock. Decline, cancellation or the 30-minute pending-payment expiry releases the hold. Expiry is evaluated when the ledger is next accessed. A late capture is rejected for reconciliation. Real provider support requires a durable exception and refund workflow for late settlement before enabling payments.
- Returns restock only on confirmed receipt; accepting a refund-only request leaves physical stock unchanged. Fulfillment, cancellation and refund actions cannot debit or credit twice. The sandbox handles a full refund of paid amounts; partial settlements and partial returns require the authoritative backend.
- SQLite commits receipt, payment reference, order and holds together. JPEG/PNG input is capped at 4 MB and 12 megapixels, signature-checked, fully decoded and rebuilt without original names or metadata. The local file is owner-only. An eventual live receipt store needs encrypted private storage, scoped operator authorization, review audit and retention controls.

Default payment availability: Bangladesh COD and manual advance; US COD, PayPal and Stripe when simulator secrets are configured; no methods for unsupported shipping. `GRIIPBUDDY_CHECKOUT_METHODS` can override the server-side allowlist by market, for example `{"BD":{"cod":true,"manual":{"advancePercent":20}},"US":{"cod":true,"paypal":true,"stripe":true}}`. This is the integration point for a future authorized admin configuration store; there is no new admin UI or bKash storefront integration.

Official references for follow-up: [Stripe signature verification](https://docs.stripe.com/webhooks/signature), [Stripe idempotency](https://docs.stripe.com/api/idempotent_requests), [PayPal webhook verification](https://developer.paypal.com/api/rest/webhooks/rest/), [PayPal request idempotency](https://developer.paypal.com/api/rest/requests/) and [PayPal capture refunds](https://developer.paypal.com/checkout/refund-payment). The sandbox does not call the official PayPal verification endpoint or any hosted provider, and does not perform real refunds.
