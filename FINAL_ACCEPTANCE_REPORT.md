# GriipBuddy Steps 6–7 — release acceptance

**Local acceptance: passed with synthetic data. Production release: no-go.** The checkout places and tracks orders, reserves stock, handles simulated settlement, accepts and reviews manual payment evidence, and supports cancellations, returns and refund recording. A customer cannot create a real order, payment or shipment with this candidate. The checkout write routes fail closed when the recovered catalog API is configured. Production and the existing live admin were untouched.

Baseline: approved Step 5 commit `8232a54`. Candidate branch: `feature/storefront-checkout`. [Checkout contracts](CHECKOUT_CONTRACTS.md) and [local setup and rollback](README.md#steps-67-isolated-checkout).

### Test and performance receipts

- **Storefront:** 16/16 baseline fixture, 7/7 recovered API and 12/12 release tests. Lint, TypeScript and optimized Next.js build passed.
- **Recovered backend:** 303 JavaScript files parsed; 20/20 baseline and 20/20 after synthetic encrypted restore (16 collections, 21 documents, 42 indexes, matching fingerprints). Shipping, payment and notification transports were simulated. Backend logic and admin UI were preserved; only the backend dependency lock changed.
- **Reconciliation:** the release checkpoint matched 18 synthetic orders and six stock rows without discrepancies. The online backup at that checkpoint also preserved two sanitized receipt blobs, six payment events and nine payment references. These fixture counts are separate from the preserved Singapore database.
- **Performance:** the production build reported 132 kB first-load JavaScript for the storefront catch-all route (103 kB shared). On loopback Chromium, homepage at 1440 px measured 11 ms to first byte, 48 ms to DOM content loaded and 367 KiB transferred. The tablet category and phone product measured 15–16 ms to first byte with warm shared assets. These are local observations without throttling, a CDN or field traffic.
- **Resolved test failures:** the first parallel run shared a Playwright trace directory and a mobile test matched a payment option as well as the transaction reference field. Separate output directories, a tighter selector and the final reruns resolved those failures. The receipt image library's initial audit finding was removed by upgrading it.

### Release gates

1. Connect all paid methods to one atomic claim on the recovered MongoDB inventory and verify last-unit contention with POS and warehouse operations. Reconcile legacy holds and stock before enabling payments.
2. Verify real PayPal and Stripe sandbox creation, callbacks, provider idempotency and refunds with authorized test credentials. Build a durable reconciliation path for late and ambiguous settlement. Verify the intended Steadfast webhook and shipment state mappings with simulated fulfillment.
3. Remediate remaining legacy dependency advisories with admin export, mail and validation regression checks. Approve real shipping, tax, support and returns settings; require private encrypted receipts, scoped staff verification, audit history and retention rules.
4. Rehearse the final artifact on isolated staging with the approved scrubbed dataset, then verify backup recovery objectives, production rollback, canonical host, index policy and edge controls. Obtain explicit production approval before any deployment.
